# Chrome Sidebar review（2026-11-18）

本次检查 background.js、sidepanel.js、peek-content.js、manifest、样式和测试。发现两个高优先级问题及多项一致性、性能问题，已修复。目录没有 Git 元数据；修改前源码及原测试保存在 `/tmp/sidebar-review.KGF6q4/`，未提交代码。

## 问题与修复

| 优先级 | 问题与触发条件 | 修复位置与结果 |
| --- | --- | --- |
| P1 | 浮窗打开后 1 秒内，从同一来源打开相同 URL，会直接删除新标签。旧逻辑先判重再检查后台标签/独立窗口，无法区分新的用户操作。 | `background.js` 的 navigation listener：移除以 URL 和时间为依据的自动关页。普通链接仍由捕获级 click handler 阻止默认打开；后台标签及独立窗口保留。 |
| P1 | OPEN_PIN 创建标签后先排序、再保存绑定。Chrome 正在拖动标签等情况下 tabs.move 拒绝，标签已打开但绑定丢失，再次点击会重复打开。 | `background.js:249`：先保存数据及绑定，再尝试调整真实标签顺序；排序失败显示可恢复提示。CLOSE_PIN 关闭失败也保留绑定，并校验窗口，避免关闭已移到其他窗口的标签。 |
| P2 | Pin/文件夹顺序全局共享，但只同步发起操作的窗口；其他窗口侧栏与真实标签顺序不一致。 | `background.js:256`：共享排序变更同步所有绑定窗口，打开/关闭 Pin 只处理当前窗口；补上删除文件夹和导入后的排序同步。 |
| P2 | 浮窗返回普通标签后控件可能残留；旧 PEEK_STATUS 响应还可能覆盖刚收到的 popup 状态。 | `background.js` 的 returnPeekToTab、`peek-content.js:48`：明确通知控件退出，并在返回成功时清理 UI；Pin 与 popup 分别维护响应版本。 |
| P2 | 创建浮窗成功，但保存浮窗元数据失败时，catch 仍执行“打开普通标签”兜底，重复打开页面。 | `background.js` 的 PEEK_OPEN：区分创建失败和后续元数据失败，后者保留已创建页面，不额外打开。 |
| P2 | ACTIVATE_TAB / MOVE_TAB / CLOSE_TAB / CLEAR_TABS 都会重写全部 Pin 和 bindings；普通标签关闭事件也无条件写 bindings。大量页面随存储变化查询浮窗状态，增加后台队列压力。 | `background.js:158`、`background.js:336`、`peek-content.js:79`：普通操作跳过 Pin 写入；其他操作仅数据变化时写入；绑定变更只通知受影响页面；状态查询独立于变更队列。 |
| P2 | 每处理一个文件夹都遍历全部 Pin/文件夹；大量 tabs.onMoved 又分别读取数据并检查顺序。 | `background.js:55`、`sidepanel.js:382`、`background.js:401`：建立父子索引，后台迭代遍历，按窗口合并尚未处理的排序事件。 |

其他改善：过滤不影响 UI 的 onUpdated 字段；窗口事件只刷新相关侧栏；开启浮窗时取消对全部既有 HTTP 页面重复注入，保留后台对 Pin/浮窗的必要注入；图标延迟加载和异步解码；激活页面加载中也显示黄色状态；设置授权过程中禁用开关；Clear 保留等待浮窗分类的标签。

## 性能证据

在同一 Node 进程中对修改前后的 `sortPinsByTree` 预热 5 次、测量 50 次，报告中位数。合成数据为平级文件夹，Pin 均匀分布。每组比较输出 Pin ID 顺序，结果一致。

| Pin / 文件夹 | 修改前 | 修改后 | 函数加速 |
| --- | ---: | ---: | ---: |
| 200 / 20 | 0.081 ms | 0.049 ms | 1.7× |
| 2,000 / 200 | 3.676 ms | 0.304 ms | 12.1× |
| 5,000 / 500 | 22.360 ms | 0.833 ms | 26.8× |

这是排序函数的微基准，不包含 Chrome API、DOM、网络和端到端交互耗时，不代表整体插件提速倍数。基准脚本：`/tmp/sidebar-review.KGF6q4/benchmark.cjs`。

回归测试另验证：普通标签动作对 Pin/bindings 写入为 0；连续 100 个同窗口移动事件只触发一次排序查询；Pin 改名不向网页发状态消息；100 轮无关数据/刷新通知不新增内容脚本状态查询。

## 验证与边界

- 原有 47 项测试通过；最终 59 项测试通过：`node --test tests/*.test.cjs`。
- `node --check background.js`、`node --input-type=module --check < sidepanel.js`、`node --check peek-content.js` 通过。
- 使用独立 profile 的 Chrome 158 headless，通过 CDP 加载真实扩展；Pin 创建、重命名、关闭、重开及文件夹弹窗提交通过，无页面错误。检查了 360 × 780 页面截图。
- 浏览器测试将 sidepanel.html 作为扩展页面打开，未覆盖原生侧栏按钮、真实拖动手势及系统快捷键。浮窗的返回、去重、状态竞争由 Chrome API mock 回归覆盖，尚未对全部站点做真实浏览器测试。
- 当前仍会为已注册匹配范围内的新 HTTP/HTTPS 页面加载内容脚本并做一次初始状态查询；本次消除了无关操作带来的重复查询。
- 极深备份层级的递归导入/前端渲染、上万行 DOM 的虚拟化，以及真实站点长时间 CPU/内存占用不在本次验证覆盖中。不能据此断言不存在其他 bug 或内存泄漏。
- 移除 URL 判重后，若网站更早在 window 级处理同一手势并创建页面，仍可能出现额外页面；插件不再通过猜测来源主动删除它。

重新加载扩展后生效。现有网页中的旧内容脚本需刷新页面或重新开启浮窗功能以替换；浮窗建议重新打开。原始快照、基准脚本和浏览器验证脚本均在上述临时目录，可能被系统清理。
